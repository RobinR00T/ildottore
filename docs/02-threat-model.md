# 02: Threat model & safety model (of the scanner itself)

A security tool that is itself unsafe is a liability. This document is **normative**: the
build must satisfy it.

## 1. Assets & actors

- **Assets**: customer credentials (`auth_ref`), target endpoints, evidence (may contain
  leaked secrets from the target), the scope authorization, the scanner's own LLM keys.
- **Legit actor**: an authorized operator running an authorized engagement.
- **Abuse actors**: (a) operator scanning an out-of-scope system; (b) a malicious *target*
  that attacks the scanner back (esp. the LLM judge); (c) exfiltration of evidence.

## 2. Safety requirements (hard invariants)

| ID | Requirement |
|----|-------------|
| S1 | **No real destructive actions.** Any tool with side effects (email/calendar/file/HTTP-write/shell/db-write) runs as a **mock or dry-run**; the scanner records the *intent* to call, never executes it. |
| S2 | **No real exfiltration.** Data-leakage tests use **canaries** (unique tokens planted by the scanner): detection = "did the canary appear in output", never real secrets. |
| S3 | **Endpoint allowlist.** Adapters refuse any host/path not in the scope allowlist. Default-deny. |
| S4 | **Authorization gate.** No run starts without a valid `scope.yaml` covering every target; scope file integrity is checksum-verified and the run records its hash. (Status: the first half holds. The integrity half does not yet: the scope's SHA-256 `checksum` is optional, verified only when present, and lives in the file it protects, so an editor can recompute or delete it. It is a checksum, not a signature: decided 2026-10-11 (OD-2, under the owner's delegation, revisable), it is signed off as integrity only, and proving who wrote or approved a scope is a non-goal until the tool has key management; an operator signs the scope out of band (SSH signatures, sigstore, a signed commit) and verifies it before the run, and the recorded digest below ties a report to the signed bytes (`docs/MANUAL.md` §4.1). Since 2026-10-05 every run records the SHA-256 of the scope text it parsed (the top-level `checksum:` line aside, so it equals a well-formed `checksum`): on a resume with `-sV` before its probe pass, otherwise with each run's integrity record (after a fresh run's probes, before its attack traffic), the run store appends it to `context_json.scope_sha256s` whenever it differs from the last entry, so a resume under a different scope is recorded and said on stderr rather than refused, and each report carries the `scope_sha256` of the invocation that wrote it. It names the record; it does not prove who wrote it, which the out-of-band signature does (OD-2). Since 2026-10-06 the record has one reading: a key written twice in one YAML mapping is refused instead of keeping the last value, which a reviewer reading the first did not approve, and so are two identities of one target with one name or one canary; `authz_leak` counts a canary written inside another for the longest one.) |
| S5 | **Payload marking.** Every payload that would be dangerous outside a test is `test_only: true` and tagged; reports never render raw dangerous payloads without a `--unsafe-render` opt-in. (Status: the marking holds, the rendering half does not. The mark is enforced from the spec's category, by `dottore lint` (`MISSING_TEST_ONLY`) and at run time, where an unmarked spec in a flagged family is `blocked_by_policy` (A-29). The opt-in is not built: there is no `--unsafe-render` flag. The HTML reporter has an internal `unsafe_render` switch, off by default and set by nothing, that adds a banner and decides whether finding reasoning is HTML-escaped; autoescape stays on and the HTML report does not show prompts. No reporter reads `test_only`, and the JSON report carries each attempt's request, prompt included: it passes through the redactor, which masks secret, PII and high-entropy shapes and nothing else, so the attack text of a `test_only` spec is readable in the JSON report.) |
| S6 | **Secret masking.** Secrets/keys are masked in logs, console and reports by a central redactor; evidence stored encrypted at rest (MVP‑2+). (Status: masking holds; encryption at rest is not built. An error the CLI prints passes through the redactor too (`cli/app._masked`), whole, URL passwords included (until #96 the URL rule ran on its own first and cut a registered credential holding an `@` or a `:`, which the redactor then no longer found); a 64-hex value stays readable only as an evidence file name (`<sha256>.json`) or as a digest the tool computed and the error carries (on a scope checksum mismatch the digest of the body, while the `checksum:` value the operator typed is not quoted at all; on a tamper refusal the hash the artifact's content has now), unless it is part of a registered credential (from 8 characters), and then it prints as `«REDACTED:credential»` (one that contains a registered credential loses it to the value rule first); every other 64-hex value goes to the redactor, unless it is part of a kept path. A spec file a load refusal names stays readable (`attacks/DL-PII-ELICIT-001.yaml`, which the entropy rule read as a key) when it is a relative path to an entry on disk under a spec path and no token character of the entropy rule is glued to it, under the same rule; the name is whoever wrote the spec tree's choice (the operator, or the author of an installed pack), so it carries nothing of the run, and a credential or PII shape in it is masked by the value and shape rules; what the loader quotes from inside the file goes to the redactor. A path stays out of the entropy rule (every other rule still applies, and a kept text holding 8 consecutive characters of a registered credential prints as `«REDACTED:credential»`) where it exists on this machine: the part of an absolute path that exists, read up to the first whitespace, a quote, a bracket, a comma or a semicolon, as before, with main's `Path.exists` calls and no cap, and since PR #70 a path that exists written whole, absolute (its directory names may hold a space or a bracket) or relative to the working directory as one word, starting and ending between characters the entropy rule does not join into a token, so the rest of the message is read as before (a report named after a commit SHA was masked before a colon, relative, or under a directory with a space). The name of a file that does not exist stays masked (OD-25), so a key given where a file belongs is masked even with an extension. The whole-path walk costs at most 1,024 filesystem lookups and 65,536 checks per error, past which it keeps nothing more; main's rule makes main's lookups or fewer, and holds nothing between tokens. An error names an `auth_ref` only when it is a reference containing `://`; a literal pasted in its place prints as "a literal value (not shown)", because the redactor recognised a raw key only by its entropy. A scope validation error names fields and reasons, never the input value. The live adapters redact a provider's string `model` echo by patterns and known credentials but not by the entropy rule, so the fingerprint can read a mixed-case name such as `meta-llama/Meta-Llama-3-8B-Instruct`; that exemption is in memory only, and the evidence store, the run store and the reports apply the full redactor to everything they keep. A mask written by the target (`«REDACTED:...»`) is kept as it is only when its type is one the tool writes; any other is read as text, so a registered credential, a key shape, a high-entropy value or a labelled value inside it is masked (2026-10-06; it used to be kept whole, key included). The trade-off: an unregistered secret that only the entropy rule recognises (an `sk-proj-` or `sk-ant-` key, a bare bearer token) placed by a target in its `model` field stays unmasked in memory for the run, and is masked wherever it is stored. A password in a URL is masked behind a registered, masked or empty user: a registered credential as the user, a mask the target wrote there, or no user at all (`redis://:password@host`) left it readable when the host had no dot (before PR #56); a user holding a raw `@` (`myadmin@srv:password@host`) still does. A registered credential holding the URL's `://`, its `:` or the password's `@` with no later `@` stopped the URL rule and left the password, or its part outside the credential, readable (before A-31 too), and two overlapping credentials masked as one run could cover the `://` the one-at-a-time replacement before A-31 left (PR #56); since #96 such a URL is read as it is written, last in each pass, and what of its password is still readable is masked. A credential holding an `@` across the URL's `@`, in the user or the password, still lets the URL rule read on to a later `@`, and since #96 a labelled value whose head that mask takes keeps its mask (PR #56 left its tail readable), and the labelled values after it are read as the redactor before #56 read them (a label in the value's tail took the next label into its value, and the secret after it was readable, on main too). Each case needs a target writing a registered credential that holds a URL separator. Left open after #96: where the URL rule did read a URL, its reading stands, so after a registered credential holding the user's `:` the rest of the user is shown (`redis://ops:svc-keyXYZ:<password>@host` with `ops:svc-key` registered shows `XYZ`, which urllib reads as the password's head); a labelled value whose label sits in the user of a URL read through a mask or behind an empty user (both read since #56), or is glued to the word before it (`...3password="x@host.tld`, a label to no version), keeps what follows the URL's `@` readable as its host, where the redactor before #56 masked it whole or as an address; the rest of a labelled value after a URL mask stops before a `://` that a `:` and then an `@` follow before any whitespace (the shape the URL rule needs, in this pass or the next), so what of the value lies past that `://` is left to the other rules (`secret=AETw://0G1h9.mGle` and U+200B before `://u:<password>@h` shows `0G1h9.mGle`); a raw `@` in a URL's user or unregistered password leaves the password, or its part after the `@`, readable; and a URL whose `://` is split by an invisible character (`s3:/<U+FEFF>/bob:...`) is read by no URL rule. An error quotes an endpoint, and an `auth_ref` holding an `@`, without what precedes the last `@` of its authority, before cutting it: the policy gate's refusal cut first and printed 287 characters of a 308-character password whose `@` fell past the cut (#96). A mask depends only on what it masks: a digest is computed over the value as written (short of a private key near the pattern's 16 KB bound, which counts each mask inside the key as a stash token whose length grows with the masks before it), so with the salt pinned a value reads the same in every process and wherever it appears (a private key's digest changed with `PYTHONHASHSEED` and with the masks before the key before PR #56), and registered credentials that overlap in the text are masked as one run (one of them was masked, by a set's order, and the other's tail was readable). Since PR #57 a registered credential split by a control character (C0, DEL, C1, U+2028, U+2029, a lone surrogate), by a format character (Unicode Cf, pinned to Unicode 16.0: zero-width characters, the soft hyphen, the bidi controls, the byte order mark, the tag characters) or by U+FFFD (what half a character in a reply reads as, A-47) is masked whole by the redactor itself (`redact_text`), with the digest of the unsplit credential, so every report, the evidence store, the run store and the terminal mask it; it used to be kept in two readable halves, except split by `\x00` or `\x01`. Not covered: a credential split by a printable character other than U+FFFD (a space included) or around a mask, an unregistered key shape split that way (unless the entropy rule takes each half), and invisible characters outside Cf. A reply kept in pieces as well as whole is masked as the text the pieces make (A-77, 2026-10-12): OpenAI's logprobs keep it as tokens of 1 to 4 characters, each with its alternatives, and a WebSocket transcript as the deltas it was streamed in, each too short for any rule, so the run's canary, an `sk-proj-` key and a registered credential were rebuilt by joining the `token` fields of the evidence and of the JSON report, and of a transcript's deltas, while `response.text` read masked (audit of main `de122e26`, HIGH 1). A logprob list's tokens, and a transcript's received content field by field (the fields the target file declares as the protocol's apart, which the transcript names), are joined and redacted once; the first piece a mask covers shows it and the others lose the text under it, so, joined, the pieces show each mask once and never more than the redacted text (less only where a literal between two masks could stand in more than one place: 8 of 1,500 realistic replies, 309 of 1,500 hostile ones), and a masked token's alternatives and `bytes` are masked with it, in a logprob list and in an event stream's chunk alike (an OpenAI chunk's `bytes` spelled a key in the excerpt of an event stream, on `main` and before the fourth pre-merge audit's fix). The evidence store's fail-closed guard redacts every such joined text as it redacts every string; a refused write, of an attempt or of a recognition probe, is stored again with the reply's pieces withheld and said so in every report and on the terminal, so a refusal no longer ends the campaign alone (pre-merge audit of `c4bd2012`, HIGH 1: a URL password masked correctly but shown in every piece read as a run the URL rule masked again, and the run aborted). An unreadable reply's excerpt is masked the same way: a WebSocket turn's frames, a JSON body's OpenAI logprobs, a body streamed as server-sent events read as the format says (lines end at CRLF, LF or CR only, an event's data lines join, data that is no JSON object or array is text of one stream), a page of `data:` lines read line by line, and JSON lines in Ollama's or OpenAI's chunk shape (any other JSON lines are records), reading only the head the excerpt can show, and withholding the streamed text of a body cut there, its keys, structure and protocol fields kept, only the lines `main`'s excerpt shows whole quoted, and of those only blank lines, JSON lines and the format's fields, and a notice saying so (the owner's decision of 2026-10-13, under the delegation, best practice: fail closed, an excerpt may show less than `main`, never more; masked across the head, a secret straddling the cut showed its beginning, fourth pre-merge audit, MEDIUM, and with only the first half shown and a stream's open tail left out, a 600-character URL password of words still showed 20 to 61 of its characters, where none shows now); a rewritten excerpt keeps the target's characters unescaped, since escaped, a phone or a card grouped by a no-break space was shown where `main` masked it (second pre-merge audit, MEDIUM 1 and MEDIUM 2). The reports mask an attempt as the store does, the keys of its free-form fields included (MEDIUM 2: `r.json` wrote a tool call's argument names, a usage field's and a frame's in clear). Not covered: a secret a target splits over a list of its own JSON that is no such stream (a REST body's array), or that its alternatives alone spell beside kept tokens, or that it encodes; in an excerpt, the shapes A-77's list names (a line that is no field of an event stream, pieces in a comment, `event:` or `id:` line, data each piece of which starts with a kept space, JSON lines in another shape or with a non-JSON line, a body mixing events with JSON lines, in a body the head cuts, a secret split over the fields kept there, which are shown no further into the body than `main`'s excerpt shows them, and others); and evidence written before A-77, which keeps its pieces. A judge's words recorded beside a cut reply are redacted before they are folded and cut (LOW 5), and an evidence file's `media_sha256` is put back unread only as SHA-256 hex digests (LOW 7). Errors, warnings, the text output of `lint`, `coverage`, `registry ls`, `describe`, `diff`, `calibrate` and `replay`, and the canaries `run --dry-run -vv` lists to seed carry no raw control character: they quote what a pack author, a report or a target wrote, and a spec file named with a newline printed a GitHub Actions workflow command on stderr (before PR #51). After the redactor, a C0 control and DEL are written as their control pictures (`␊`, as the redactor writes `␀` and `␁`), and a C1 control, U+2028, U+2029, a lone surrogate and a format character (Unicode Cf: zero-width characters, the soft hyphen, the bidi controls that reorder what is read, the byte order mark, the tag characters; since PR #51) as Python escapes, after the redactor has masked a credential they split (above); U+FFFD, which shows, is printed as it is. The run's error and coverage lines are printed unwrapped, `coverage` lists unloaded files as bullets and `diff` refuses a report whose spec ids are not spec ids, so none of those lines starts with such text. A runner also reads a command in the middle of a line: GitHub Actions the legacy `##[cmd]` form, Azure Pipelines `##vso[area.event]`. Those paths write the second `#` of `##<letters>[` as `\x23` (`#\x23[error]`), and so do the off-universe values `coverage` and the run's summary print as their `repr`, the reasons the `-vv` plan gives for a spec the policy pack refused, which quote its `requires_policy`, and the scope digests the resume note reads back from the run store (written as they were before PR #54; verified by feeding the CLI's lines to the GitHub runner's own `OutputManager`, where they raised annotations and, from a spec's name at the end of a `registry ls` line, an `add-mask` that hid `FAIL` in later lines and a step output, and to the Azure agent's parser). The JSON outputs keep a value as it is and, since OD-20 (decided 2026-10-11), write that same `#` as `\u0023`, JSON's own escape for it, so printed to a CI log they carry no such command and any JSON reader parses the same value (`lint --json`, `coverage --json`, `dottore fingerprint`, `schema export`, the JSON and SARIF reports; the JUnit XML report as `&#35;`, the character reference an XML parser reads as `#`). Not covered: a `replay` line started by an id from a forged evidence tree, the operator's own values in the run's plan lines (the target id under `--dry-run`, `--estimate` and `-sn`), and invisible characters outside Cf (variation selectors, U+034F, U+3164), which print as they are.) |
| S7 | **Judge isolation.** The LLM judge treats target output as **untrusted data**, never as instructions (see `docs/04 §4`). A target that jailbreaks our judge must not flip a verdict. |
| S8 | **Rate & cost caps.** Hard token, request, attempt and wall-clock budgets (`core/budgets.py`), sized from the resolved plan so a ceiling never truncates a scan in silence, **plus** an enforced request-rate ceiling (`core/pacing.py`, `--rate` / `-T`): one shared gate for the whole campaign, so concurrency cannot multiply it, and retries count against it. The scanner cannot be turned into a DoS weapon by a spec. (The rate half of this row was aspirational until 2026-09-21: `--rate` was parsed and dropped, so `--rate 0.0001` finished eighteen specs in 0.67s. Pacing is not applied to an offline mock run, where nothing leaves the process, and the resolved plan states that explicitly. The `--judge` model and the multi-identity sweep sent outside both halves until 2026-10-03; they now pass the same gate and debit the same ceilings, retries happen in one layer so each one counts, and `--rate` must be greater than 0. The token axis is trued up to the usage a reply reports, which is the target's own figure: since 2026-10-07 a figure that is not a JSON integer from 0 to 2^53 is not believed: the next shape the reply reports is read, a pair beside a prompt-cache figure that is there and unreadable only trues the reservation up, and a reply with no readable shape keeps its reservation, where a 400-digit one made the run exit 1 with no report and one past 2^53 halted it after one reply. Up to 2^53 it is believed, so a target can still end a campaign early on the token ceiling (reported as `budget_exhausted`, with the specs that never ran), or free its reservation by reporting less; clause A-36 in u08.) |
| S9 | **Blast-radius for RAG/agent setup.** Test corpora are namespaced and torn down; the scanner never writes to a production index without an explicit, scoped, reversible flag. |

## 3. Legal / ethical framing

- The tool assists **authorized** security testing only. The scope file *is* the
  authorization record. Runs are meant to be auditable (who/what/when/scope-hash). Today a run
  records the *what* (spec digests, target digest, judge digest, run count, planning mode) and
  *when* (`started_at` / `finished_at`, UTC, in the run store and the JSON report, since
  2026-10-04; a resume keeps the start of the run it finishes) and *under which scope* (since
  2026-10-05: the run store keeps each scope the run went out under, in order, and a report
  names the scope of the invocation that wrote it), and not the operator. Attempts and probes
  carry no time of their own.
- This is a defensive/assurance tool: it validates that a model or AI app resists known
  attack classes. It is not a jailbreak-as-a-service.

## 4. Attacks against the scanner (and mitigations)

| Threat | Mitigation |
|--------|------------|
| Malicious target output prompt-injects the **judge** and flips verdicts | Judge hardening (`docs/04 §4`): output wrapped in data delimiters, judge told it evaluates untrusted data, self-check probes, disagreement → `inconclusive`. (Status: the judge evaluator returns `inconclusive` on a disagreement between its two passes, but with no reason, and the runner drops a reasonless judge abstention: the attempt is decided by the deterministic evaluators alone, a `pass` when they all pass, and is `inconclusive` only when the judge is the spec's sole evaluator. Whether a disagreement should keep the attempt `inconclusive`, as this row says, is an open question for the owner, `docs/04 §2`. A judge that emits the tripwire, or reports an injection while saying `secure`, is `judge_compromised` and is kept.) |
| Evidence contains real leaked secrets | Redactor + at-rest encryption + access controls; canaries preferred over real secrets. (Encryption at rest is MVP-2+ and not built, see S6.) |
| Spec pack from a third party contains a malicious payload / SSRF carrier | Spec linter + policy pack allowlist + `test_only` enforcement + no network from spec loading (`docs/06 §5`). |
| Malicious target reply built to crash or exhaust the scanner (oversized, a compression bomb, JSON nested past the parser's stack) | Every reply is read through a 4 MiB cap, decoded inside it, and parsed with its nesting bounded at 100 levels (`docs/MANUAL.md`, bounded replies; contract u04 §4): a refused reply is an inconclusive attempt, not retried, and the campaign goes on. (Status: since 2026-10-11 (OD-21, decided under the owner's delegation, revisable) a 200 the adapter cannot read, not JSON, not an object or not the provider's shape, is refused the same way, inconclusive (`unreadable_reply`) and not retried, and its spec is never a pass, since a wrapper broken by the quotes of a jailbreak that worked is the attempt that may have succeeded; it keeps a redacted excerpt and every report counts it; replies that cannot be read 5 in a row before any was read, or 20 in a row after, stop the campaign when one benign check sent then cannot be read either (u08 A-74), so a wrong endpoint is caught for 6 requests and a target that breaks mid-run for 21, while a filter that answers attack prompts with a block page lets the check through and the battery finishes. It used to stop the campaign at the first one. Since PR #68, a refused reply during a `-sV` or `-A` probe pass fails only that probe and the run goes on, where before it stopped the run before the attack, contract u09 §7 A-35, open decision OD-23.) |
| Operator scans out of scope | S3/S4 default-deny gate. |
| Cost blow-up (recursive/expensive specs) | S8 budgets, enforced in the runner, not the spec. |
| Malicious target reply holding half a character (a lone surrogate) that no UTF-8 writer accepts | Read as U+FFFD where the reply is parsed (contract u04 §7, A-47), so the evidence store, the run store and the next request can hold it, and the attempt is still judged: refusing the reply would let six characters hide a leak. (Status, 2026-10-09: decided as built, OD-28; not deleted, which UTR #36 advises against. Half a character inside a word splits it as a zero-width space does: `regex_absence` misses a leak split that way (inconclusive, exit 0), `secret_leakage` misses a split canary, and the spec passes when a judge says secure, its own task; a registered credential split that way is masked whole, as S6 says.) |

## 5. Out of scope (v1)

- Actual model weight extraction, training-data reconstruction, or any technique requiring
  privileged/internal access beyond the target's normal interface.
- Real exploitation of downstream systems reached via tool calls (always mocked).
